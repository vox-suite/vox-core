# Primary-source notes for the Vox Core durable-task performance investigation

These are design and measurement constraints, **not measured Vox Core results**. The implementation under study is the `vox-core` API and worker at the September 2026 checkout.

## PostgreSQL claim and query analysis

- PostgreSQL explicitly identifies `FOR UPDATE SKIP LOCKED` as suitable for multiple consumers of a queue-like table because it avoids waiting on locked rows. It also warns that the result is an inconsistent view and that table-level locks can still wait. Measure claim latency and throughput under competing workers; do not interpret a skipped row as missing work. [PostgreSQL `SELECT`](https://www.postgresql.org/docs/current/sql-select.html)
- A partial index helps only when the planner can prove the query predicate implies the index predicate, and key order still matters for the query's filter and `ORDER BY`. Vox Core's current claim orders by `jobs.created_at`, whereas `jobs_queued_idx` starts with `available_at`; whether a new index improves claims is a benchmark question, especially for mixed pending and expired-lease branches. Compare plans and timings at multiple queue depths before recommending a migration. [PostgreSQL partial indexes](https://www.postgresql.org/docs/current/indexes-partial.html); [Core claim SQL](../../src/durable_tasks/mod.rs); [Core index migration](../../migrations/20260923000000_initial_core.sql)
- `EXPLAIN (ANALYZE, BUFFERS)` executes the statement and reports actual node times, rows, and buffer use. For the mutating claim query, run it in a transaction and roll back, then verify that the rollback restored benchmark state. `EXPLAIN` is server-side evidence, not a substitute for client-observed latency. [PostgreSQL `EXPLAIN`](https://www.postgresql.org/docs/current/sql-explain.html)
- `pg_stat_activity` exposes backend state and wait events, while `pg_stat_statements` aggregates normalized query calls, execution time, rows, and buffer activity when enabled. Use these to diagnose server contention alongside application timings; aggregate statement statistics cannot supply per-request tail percentiles. [PostgreSQL monitoring statistics](https://www.postgresql.org/docs/current/monitoring-stats.html); [`pg_stat_statements`](https://www.postgresql.org/docs/current/pgstatstatements.html)

## Connection-pool and tail-latency methodology

- SQLx's pool waits when all connections are checked out, and `acquire_timeout` covers more than semaphore wait: it can include liveness checks, connection creation, handshake, and hooks. Time explicit acquisition separately from transaction/query execution, and record pool size, idle connections, and timeout counts before attributing delay to PostgreSQL. Size the API and worker pools together against the server's connection budget. [SQLx `Pool`](https://docs.rs/sqlx/0.8.6/sqlx/struct.Pool.html); [SQLx `PoolOptions`](https://docs.rs/sqlx/0.8.6/sqlx/pool/struct.PoolOptions.html)
- Report latency distributions for each workload and concurrency level. Google's SRE guidance explains why means conceal long tails and why queueing amplifies variance at high load. Report the sample count with each percentile: p99.9 is only an order statistic with roughly one observation in the slowest 0.1% per 1,000 samples, so smaller runs cannot establish a stable p99.9. Treat that sample-count rule as a statistical inference, not a Google guarantee. [Google SRE, Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)

## Tracing, wakeups, and provider boundaries

- OpenTelemetry defines database client spans around the call as observed by the caller and separate connection-pool metrics including pending requests, timeout count, and wait time. Use low-cardinality operation labels; capture query text only after sanitization. Record API authentication, DB acquisition, SQL execution, transaction commit, worker claim, queue residence, provider call, status emission, and authoritative read as separate spans or benchmark stages. [OpenTelemetry database spans](https://opentelemetry.io/docs/specs/semconv/db/database-spans/); [database client metrics](https://opentelemetry.io/docs/specs/semconv/db/database-metrics/)
- The general job worker polls every 30 seconds; the separate status-webhook delivery loop polls every one second. If evaluating `LISTEN`/`NOTIFY` as a job wakeup, PostgreSQL delivers notifications on commit and documents a startup race; the durable jobs table must remain the authority and the worker must scan after subscribing and periodically recover from missed wakeups. This is a design inference from the documented semantics, not a measured improvement. [Core job worker loop](../../src/workers/mod.rs); [status delivery loop](../../services/worker/runtime.rs); [PostgreSQL `LISTEN`](https://www.postgresql.org/docs/current/sql-listen.html); [`NOTIFY`](https://www.postgresql.org/docs/current/sql-notify.html)
- Redis Pub/Sub is at-most-once: a disconnected subscriber loses events. Status events can therefore reduce perceived delay but cannot replace the PostgreSQL authoritative status read. [Redis Pub/Sub delivery semantics](https://redis.io/docs/latest/develop/pubsub/)
- The task executor makes a Gemini call through `rig` and awaits the full response before persisting completion. Time the client-observed provider call separately from Core work; this interval includes network and client overhead and does not identify provider-side compute on its own. Google's Gemini documentation says longer inputs generally increase time to first token, so record prompt size and model/configuration without recording user instructions or generated content. [Core executor](../../src/workers/task_executor.rs); [Gemini long-context guidance](https://ai.google.dev/gemini-api/docs/long-context); [OpenTelemetry HTTP client span boundary](https://opentelemetry.io/docs/specs/semconv/http/http-spans/)
